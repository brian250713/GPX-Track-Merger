## Context

`computeElevationProfile(day)` 已經走過每個段落的每個點，累積里程、挑出有 `ele` 的點、記錄 `minEle`／`maxEle`，並以「可用點數 < 2」作為 `hasData` 的判定。累積爬升需要的輸入與這條走訪路線完全相同，差別只在於要在走訪過程中多維持一個狀態。

展開區塊目前的結構由 `swap-summary-and-stats` 定下：

```
.day-expanded-wrap  (display:flex; flex-wrap:wrap)
  ├─ svg                 flex: 1 1 320px;  max-width: 420px    ← SVG 自己就是 flex item
  │   或 .elevation-empty flex: 1 1 320px;  max-width: 420px
  └─ .day-time-stats     flex: 1 1 260px
```

`tests/layout.test.ts` 有兩條斷言釘住這個結構：`2.1` 要求 `.elevation-container svg` 規則內含 `max-width: 420px` 且不含 `max-width: 100%`；`3.2` 要求同一條規則內含 `flex: 1 1 320px`。

GPX 的高度來源有兩種：氣壓計（Garmin、Suunto 等運動錶，雜訊約 ±1–3m）與衛星高度（手機，雜訊約 ±3–10m，且與水平定位誤差相關）。這個 app 的主要輸入是旅行中用手機錄的軌跡，所以要以衛星高度的雜訊水準為準。

動機見 proposal.md；行為契約見 `specs/` 下的三份 delta。

## Goals / Non-Goals

**Goals:**

- 算出的爬升數字在平路上接近 0、在真實爬坡上接近真值，兩邊都不能失守。
- 爬升的分段規則與距離、行進時間、剖面里程四者完全一致，不會出現「搭飛機到高原被算成爬升 2000 公尺」。
- 門檻是一個具名、匯出、寫進規格、在 README 揭露的常數，和既有的斷訊門檻同一種待遇。
- 沒有高度資料時顯示明確狀態，不出現 `0 公尺`、`NaN` 或空白。
- `renderElevationSvg` 的輸出一個位元都不變。

**Non-Goals:**

- 不做高度平滑、不做依距離重取樣、不校正氣壓計漂移。
- 不讓門檻變成使用者可調的設定。多一個旋鈕就多一組要解釋的數字，而且使用者沒有判斷依據。
- 不在剖面圖 SVG 上畫爬升（SVG 已經有四個 `<text>`，再加會擠，也會踩到 `tests/elevationProfile.test.ts` 逐點比對的斷言）。
- 不把下降放進統計區塊與圖卡（只在分天層級顯示，理由見 Decisions）。
- 不做每段落的爬升明細、不做爬升速率（VAM）、不做坡度分佈。

## Decisions

### 用門檻累積，不用相鄰差加總

相鄰點正負差直接加總 `sum(max(0, e[i] - e[i-1]))` 是錯的，而且錯得很大：雜訊的每一次上跳都被計入，誤差隨點數線性成長。以 ±4m 的衛星高度雜訊、10 秒取樣、走 6 小時計算，光雜訊就能產生數百公尺的假爬升，平路與爬坡的數字會分不出來。

門檻累積維持一個參考高度 `ref`，只有偏離超過門檻才提交並把 `ref` 移到當前點：

```
ref = 該段第一個有 ele 的點
每個有 ele 的點 e：
    d = e - ref
    d >  +T  →  ascent  += d;   ref = e
    d <  -T  →  descent += -d;  ref = e
    否則     →  不動作
```

關鍵性質是**單調變化不會被低估**：100 公尺的坡就算每步只上升 1 公尺，`d` 會從 `ref` 一路累積到超過 `T` 才提交，總和仍然是 100 公尺，只在方向反轉處損失最多一個 `T` 的尾巴。而在門檻內來回震盪的雜訊永遠碰不到 `T`，完全不累積。

比另外兩個候選好的地方：移動平均平滑需要選窗長，窗長太短擋不住雜訊、太長會削掉真實的短陡坡，而且窗長對取樣率敏感（10 秒一點與 1 秒一點的同一條路會得到不同答案）；依距離重取樣要先處理「停在原地時距離不增加」的退化情況。門檻累積對取樣率不敏感，這對一個要吃各種來源 GPX 的 app 很重要。

### 門檻 5 公尺，嚴格大於

5 公尺對應衛星高度的雜訊上緣。氣壓計裝置常用的 3 公尺在這裡會太鬆——手機軌跡仍會漏進假爬升，而這是本 app 的主要輸入。往上取 10 公尺則會開始削掉真實的小起伏。

比較用嚴格大於（`d > T`），不是大於等於。常數讀作「超過 5 公尺才算」，5.0 本身落在忽略帶內。浮點下兩者幾乎沒有實務差異，但規格必須挑一個，否則邊界測試寫不出來。

上升與下降共用同一個門檻。不對稱沒有物理依據，而且會讓原路折返的路線出現 `爬升 ≠ 下降` 的怪數字。

### `ref` 在每個段落開頭重置

距離、行進時間、剖面里程三者都遵守「斷開處不累計」。爬升不遵守的話，搭飛機從平地到高原會被算成一次 2000 公尺的爬升——這正是斷訊切段當初要擋掉的那類假資料。

缺 `ele` 的點直接跳過，`ref` 在段落內沿用不變。這與剖面圖「缺高度的點不納入剖面但照常計入里程」是同一個處理方式：缺高度的點不提供高度資訊，但也不應該中斷它前後兩個點之間的高度關係。

### 資料不足時沿用 `hasData`，不顯示 0

`hasData` 的判定（可用點數 < 2）與剖面圖共用同一個定義，不另立一套。可用點數不足時，`ascentM` 與 `descentM` 回傳 0，但 UI **不顯示數值**，改為沿用既有的「該天沒有高度資料」說明文字。

顯示 `爬升 0 公尺` 是主動的誤導：使用者無法分辨「這天是平路」與「這天的 GPX 沒有高度欄位」。整趟層級同理，`totalAscentM(days)` 在所有天都沒有高度資料時回傳 `null`，統計區塊與圖卡據此整項省略，而不是顯示 0。

### 爬升放在剖面圖下方，不併進 `.day-time-stats`

爬升是這張剖面圖的摘要，不是時間統計。併進 `.day-time-stats` 會讓那個區塊變成七個數字的雜燴，高度與時間混在同一個 grid 裡沒有視覺分組，而且 `time-and-pace` 這個能力的「呈現位置」需求會被迫接納非時間內容——名實不符。

代價是需要一層欄容器：

```
.day-expanded-wrap
  ├─ .day-elevation-col     flex: 1 1 320px;  max-width: 420px   ← 上限移到這裡
  │    ├─ svg               width: 100%
  │    └─ .day-elevation-stats
  │   或（無高度資料時）
  │    └─ .elevation-empty
  └─ .day-time-stats        flex: 1 1 260px                      ← 不動
```

`flex` 與 `max-width` 從 SVG 移到欄容器上。這不是為了改行為——剖面圖的 420px 上限、窄容器隨寬度縮放、放不下時換行堆疊，三條規格全部原樣成立；只是施加點從 flex item 本身移到了它的容器。`tests/layout.test.ts` 的 `2.1` 與 `3.2` 兩條斷言要跟著改選擇器。

把 `max-width: 420px` 留在 SVG 上只為了讓舊斷言繼續綠燈是不行的：那會留下一條與外層重複、語意不明的死規則，下一個讀 CSS 的人得花時間確認哪一條在生效。斷言是用來釘住行為的，選擇器變了就該跟著變。`.elevation-empty` 的 `flex` 與 `max-width` 同理一併卸下。

### 下降只在分天層級顯示

分天層級顯示爬升與下降兩個數字，因為單日的 `↑` 與 `↓` 差距本身有意義（今天是淨爬升還是淨下降、是不是原路折返）。

整趟層級只顯示爬升。多天旅行幾乎一定是回到出發點附近，總下降會是總爬升的近似鏡像，並排顯示兩個幾乎一樣的大數字只是增加噪音。圖卡同理，而且圖卡的空間更貴。

### 圖卡用「爬升」兩個中文字，不用箭頭符號

`cardFontSample()` 決定了哪些字元會被 `document.fonts.load()` 預載。用 `↑`（U+2191）的話，Fredoka 很可能沒有這個 glyph，第三顆 pill 會掉到 fallback 字型，和另外兩顆長得不一樣——而且這種問題在開發機上常常看不出來（系統字型剛好有），只在別人的機器上爆。中文字走的是 `Chiron GoRound TC Variable`，該字型本來就在預載清單裡，只要把「爬升」加進 sample 字串即可。

分天摘要的畫面上可以用 `↑`／`↓`，那裡走的是一般網頁字型堆疊，沒有預載限制。

## Risks / Trade-offs

- **門檻是個沒有唯一正確答案的數字** → 5 公尺是針對手機軌跡的選擇。使用氣壓計裝置的使用者會覺得數字偏保守（略低於錶上顯示的值）。緩解方式是在 README 揭露門檻，讓數字對不上時有解釋可查，而不是讓使用者猜。這與斷訊門檻（30 分鐘／5 公里）的處理方式一致。
- **動到前一個 change 留下的 CSS 斷言** → 見上。規格層行為不變，手動驗收仍要涵蓋 1280px／900px／400px 三個寬度，已列進 tasks。
- **第三顆 pill 的寬度** → 圖卡可用寬度 1968px（2160 − 96×2）。三顆 pill 在 `700 52px` 下即使數值都取最大位數（如 `365 天`、`9999.9 km`、`爬升 99999 m`）估算仍在 1200px 以內，不會溢出。`fitLegendDays` 那種截斷邏輯不需要複製到 pill 上，但 tasks 裡要有一個最大位數的實測驗證，避免估算失準。
- **jsdom 沒有排版引擎也沒有 canvas** → `.day-elevation-col` 的實際換行行為與圖卡第三顆 pill 的實際位置都無法用單元測試斷言，只能斷言 CSS 檔案內容、DOM 結構與純函式輸出。真正的版面要靠手動驗收，已列進 tasks。這與 `card.test.ts` 既有的覆蓋形狀一致，不是本次新增的缺口。
