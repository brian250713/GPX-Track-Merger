## Context

`.bento` 用 `grid-template-areas` 排版，欄寬是 `380px 1fr`：左欄固定、右欄彈性。分天摘要與統計目前佔用 `"summary stats"` 這一列，位置完全由 area 名稱決定，與文件順序脫鉤。窄螢幕（`max-width: 800px`）另有一份單欄的 area 字串。

展開區塊 `.elevation-container` 由 `rowBody()` 產生，內容是 `${eleHtml}${timeHtml}` 兩段平鋪的 HTML，沒有包覆元素。剖面圖是 `viewBox="0 0 320 150"`、沒有 width/height 屬性的 inline SVG，CSS 給它 `width: 100%; height: auto`，因此是純等比縮放——包含 `font-size: 11` 的標籤在內。

各寬度下分天摘要卡片的實際內容寬（扣掉 `#app` padding 24×2、卡片 border 3×2、卡片 padding 20×2、`.elevation-container` padding 8×2）：

| 視窗 | 現在（固定欄） | 對調後（彈性欄） |
| --- | --- | --- |
| 801px | 318px | 287px |
| 900px | 318px | 386px |
| 1280px | 318px | 766px |

動機見 proposal.md；行為契約見 `specs/` 下的三份 delta。

## Goals / Non-Goals

**Goals:**

- 版面上的欄寬與區塊的內容量相稱，且這條理由寫進規格，之後不會被無聲改回去。
- 視覺順序、文件順序與鍵盤焦點順序三者一致。
- 剖面圖在任何容器寬度下，標籤字級都維持在可讀範圍。
- 不動 `renderElevationSvg` 的輸出，既有的 SVG 單元測試一行都不用改。

**Non-Goals:**

- 不重新設計統計區塊的內容（大數字 pill、每日色點圖例等）。本次只搬位置。
- 不調整斷點或欄寬定義（`380px 1fr`、`max-width: 800px` 維持原值）。
- 不讓剖面圖變成寬度感知的 SVG（不依容器改 `W`、不重算刻度密度）。
- 不把時間統計或剖面圖放進圖卡。

## Decisions

### 剖面圖用 CSS `max-width` 設上限，不改 `W`

`W = 320` 是 `viewBox` 的座標系寬度，不是渲染寬度。改大 `W` 會連帶改變所有刻度、標籤位置的座標計算，並讓 `tests/elevationProfile.test.ts` 裡逐點比對路徑的斷言全部失效——而這些斷言正是剖面圖正確性的主要防線。

用 `max-width` 則完全落在 CSS 層：SVG 的輸出不變，縮放倍率從「容器寬 ÷ 320」改為「min(容器寬, 420) ÷ 320」。

上限取 420px，等於 1.31 倍縮放，標籤實際字級約 14.4px：比現在的 11px 好讀一點，又不會和旁邊 13px 的時間統計數值搶注意力。取 320px（1:1）會讓圖在寬欄裡顯得過小，取 480px 以上標籤就接近內文字級了。

窄螢幕不需要例外處理：400px 視窗時容器內寬約 314px，本來就小於上限，`max-width` 不會生效，`elevation-profile` 既有的「窄螢幕排版」需求完全不受影響。

### 展開區塊改為並排，用 flex-wrap 而非 media query

上限讓剖面圖在 1280px 下只用掉 766px 中的 420px，剩下約 346px 的留白正好落在視線中央，看起來像沒做完。把時間統計移到右邊填滿，寬欄才真的換到東西。

用 `flex-wrap` 而非 media query：剖面圖 `flex: 1 1 320px; max-width: 420px`，時間統計 `flex: 1 1 260px`，容器放不下兩者的 flex-basis 時自動換行成上下堆疊。斷點因此跟著容器寬度走，而不是視窗寬度——這正是我們要的，因為對調後分天摘要的容器寬度不再等比於視窗（見 Context 的表）。用 media query 的話，801–900px 這段就得另外猜一個閾值。

`.day-time-stats` 既有的 `repeat(auto-fit, minmax(100px, 1fr))` 不用改：在右側較窄的容器裡它會自己收成兩欄。

### 文件順序與 area 名稱一起改，不只改 CSS

`grid-template-areas` 讓視覺位置與文件順序脫鉤，所以只改 CSS 的話，左邊的統計區塊在文件裡仍排在分天摘要之後：螢幕閱讀器會先讀右邊、再讀左邊，Tab 鍵進入分天摘要的日期列之後才會回頭。

反過來只改 `main.ts` 的文件順序則毫無效果——兩份 area 字串把位置釘死了。兩邊必須一起改，這不是二選一。

### 中等視窗變窄，本次接受

801–900px 區間分天摘要會比現在窄（最窄約 287px，少 31px）。已與需求提出者確認接受，理由：

- 287px 仍然放得下剖面圖，`elevation-profile` 的「不出現水平捲軸」需求在 400px 都成立，287px 更不會破。
- 這段區間的兩個候選解法都有額外代價：把斷點從 800px 拉高會讓平板橫放提早退成單欄；把欄寬改成 `minmax(…, 380px)` 會連帶影響上傳區、檔案列表與地圖的寬度，牽動範圍遠大於本次。
- 若之後真的困擾，補救手段（拉斷點）與本次的改動互不衝突，可以獨立進行。

## Risks / Trade-offs

- **中等視窗的分天摘要變窄** → 見上，已確認接受。
- **統計區塊會被分天摘要撐成一張高的空卡** → grid 預設 `align-items: stretch`，這個現象現在就存在，只是從 828px 寬變成 380px 寬，浪費的面積少約五成。本次不加 `align-self: start`：短卡下方留一段空隙在便當盒版面裡反而突兀，等統計區塊的內容長大後再一併處理。
- **jsdom 沒有排版引擎** → `grid-template-areas`、`flex-wrap`、`max-width` 的實際效果無法用單元測試斷言。測試只能斷言 CSS 檔案內容與 DOM 順序，真正的版面與剖面圖尺寸要靠 1280px／900px／400px 三個寬度的手動驗收，已列進 tasks。
